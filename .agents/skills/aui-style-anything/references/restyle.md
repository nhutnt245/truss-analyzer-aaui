# Restyle an app or page you keep

Make an existing app or page follow AtomicAUI (the whole app, some pages or one element) and keep it on its own stack: plain HTML, Razor, Blazor, MVC, a framework, a page shown inside another app. Its logic, texts and controls stay. Only the look changes, and you prove it.
A React app moved page by page into a new app made from this kit is `../atomicaui/references/paths/convert.md`, not this page. A piece that no page has yet: `SKILL.md`. Internal use only.
You can do every step with an assistant or by hand. Every command is Node and runs the same on Windows and macOS.
Run the commands of this page in the app's root folder (the folder that holds its pages, scripts and stylesheets; in an MVC app the one with `Views/`, `Content/` and `Scripts/`): `GAPS.md` and `restyle/` are read and written in the folder a command runs in, and `restyle-done` looks there for the scripts your pages load.

## What never changes
- Logic, handlers, ids, names, values, validation and every text stay as they are (AUI-07, AUI-08). An odd text is kept and listed.
- A control a host or another application draws itself (Aras forms, grids, toolbars, or a form another application owns) is never restyled, aligned or edited: the only offer is colours by configuration, and you always leave one `GAPS.md` line (`../atomicaui/references/packs/aras/start.md`, `references/align.md`).
- Old classes, colours and pixel values do not come along. Delete them when the recipe or part replaces them. **The old stylesheet is deleted, never re-tokened, renamed or copied into a new one, and no new app stylesheet is written** (one exception, below): a page ends with `aui/aui.css`, `aui/aui-setup.css` and, for an aligned widget, its own stylesheet and `aui-align.css`. The only CSS of your own is the outer-page `<style>` block of the layout recipe (`html, body { height: 100% }`, the body a flex column) with its `/* why: */` comment, which `check-standard` reads. The one exception: the small stylesheet of show and hide rules a kept widget script needs (`references/maps/bootstrap.md`), kept with `--keep` and its line in `GAPS.md` (step 6) and read by `check-standard` like this block. A look the recipes lack is a styled piece (`SKILL.md`) or one line in `GAPS.md`, never a CSS rule of your own (a raw `min-width` or a surface colour in a new `equipment.css` was a failed restyle).
- **Markup and style a script writes is look.** An HTML string in a `.js` file (or a `<script>` of the page), `style=`, `align=`, `bgcolor=`, `border=`, `cellpadding=`, a `width` on a cell, `<font>` or `<center>` in it, and `element.style` set to a colour, background, border, padding, margin or font are the old look, as much as the same in the page: re-class them in the script (write the recipe's whole class list into the string, delete the attribute or the assignment), keep the logic around them, and list each changed line (file and line) in your final message. Showing and hiding (`style.display`), sizes and positions stay. `check-standard` reads the `.js` files of the scope and the `<script>` blocks of its pages for the forms above (AUI-02): an HTML string, `element.style.<property> =`, `style.cssText`, `style.setProperty(...)`, `element.style = '...'` and `setAttribute('style', ...)`. In the same strings a `<table>`, `<input>`, `<select>`, `<textarea>` or `<button>` with no AtomicAUI class is a hand-styled control, as on a page (AUI-01): a result table a script draws (`'<table><tr><td>' + name + ...`) gets its recipe's class lists in the string, also when it has no old attribute at all. **It does not read every form yet, and a look in one of these passes the check unread**: an event-handler attribute that sets a style (`onmouseover="this.style.backgroundColor='#ffc'"`, `onclick="this.style.color='red'"`), jQuery `.css(...)` and `.attr('style', ...)`, `.attr('align', ...)` and the like, `el.style['color'] = ...`, `el.align = ...`, `el.bgColor = ...`, `el.border = ...` or `el.cellPadding = ...`, `setAttribute('align', ...)` and the same with `'bgcolor'`, `'border'` or `'cellpadding'`, a width set on a cell (`cell.width = ...`, `setAttribute('width', ...)` on a `td`, `th` or `col`), and `createElement('font')` or `createElement('center')`. Search your pages and scripts for them (`.css(`, `.attr(`, `.style[`, `.align`, `.bgColor`, `.width =`, `.border =`, `.cellPadding`, `setAttribute(`, `createElement('font'`, `createElement('center'`, `this.style` in an `on...` attribute), re-class each by hand the same way, and list each changed line. A width or height on anything but a cell is behaviour and stays: on an image (`img.width = ...`), on a canvas, in `element.style` (`el.style.width = ...`). The check leaves other people's scripts alone, and names how many on its last line: a file called `*.min.js` or `*.bundle.js`, a library by its exact name with at most a version after it (`jquery.js`, `jquery-3.6.0.js`, `bootstrap.js`, `modernizr-2.8.3.js`, `moment.js`, `knockout-3.5.1.js`...), and the folders `lib/` and `vendor/`. Every other `.js` file is read as yours. A line of yours that must stay carries `check-allow: AUI-02` (a control with no class: `check-allow: AUI-01`) with its reason. **A library the app did not write is never edited and never given a `check-allow` comment** (jQuery and its plugins, jQuery UI, Bootstrap, Modernizr, Respond, SignalR): when the check reads one as yours (`jquery.validate.js`, `jquery-ui-1.12.1.js`, `respond.matchmedia.addListener.js`), give the check your own script files by name instead of their folder (step 5), or keep the library in a folder named `lib/` or `vendor/`, which the check never reads (moved there, the page or bundle that loads it gets the new address).
- **Every element keeps its role and behaviour.** A tree stays a tree (`role="tree"`, `treeitem`, its folding), a link stays a link (`<a href>`, the same address), a button, a list and a picked row stay what they were: `restyle-compare` fails a control whose role or name is gone. An element with no recipe is restyled all the same: its markup, roles and behaviour stay, and its look comes from the kit's tokens and the styling of the nearest part (level 3). What cannot be styled is one line in `GAPS.md`. Never a look-alike made of `div`s, never a placeholder in its place.
- **Nothing the old page lacked (AUI-07).** No chip, badge, tone, icon or colour by meaning where the old page had plain text. A status that was text stays text. A chip recipe is for an element that was already a badge or chip.
- **Restyle exactly what the task asks for**: the whole app, some pages, or one or two elements. A prompt that names no page and no element ("Make this page follow our design system") is the whole app: every page `specs/` names and every page file of the app's folder, none left on the old look (`restyle-done` fails a page that still links the old stylesheet). Everything outside that scope is listed in `restyle-map.md` as not done (step 2). A stylesheet, layout or partial that a page outside the scope also uses changes only when the scope covers every page that uses it: in Razor Pages or MVC the shared layout (`_Layout.cshtml`, given to a folder by `_ViewStart.cshtml`) is edited only when all its pages are in scope; otherwise it stays as it is, and a page in scope is set up as a page you do not own (step 1).

## The four levels. Try them in this order, and say which one you used for each kind of element.
| Level | When | What changes | Check |
|---|---|---|---|
| 1 Replace | AtomicAUI has the control (select, tabs, dialog, chip, checkbox, tree) | The markup becomes the recipe; select, tabs and dialog behaviour comes from `aui/aui-behaviour.js`, and checkbox and tree behaviour from the recipe's "You add" line; your handlers, names and values stay | `check-standard`, `check-behaviour` |
| 2 Re-class | The element is already right (button, input, label, table, heading, a box) | Only its class list: the recipe's, whole. Old classes and style attributes go | `check-standard` |
| 3 Compose | No part, and it only shows things or is one thing to click, or its own behaviour stays (below) | The style-anything steps (`SKILL.md`): roles, tokens, a marker, and ``- Styled piece `<name>`: what was missing, which screen, which file`` in `GAPS.md` | `check-standard` |
| 4 Align | It cannot be replaced: a third-party chart or grid. Never a control a host or another application draws: that is the stop above | Nothing in its markup. Its own settings first, then one marked stylesheet (`references/align.md`) | `check-conformance` only |
Nothing fits, and it takes typing, a popup or arrow keys (a menu): it is restyled by the level 3 steps all the same. Its markup, roles and behaviour stay (its own script, never rebuilt; a library's widget script stays with one `GAPS.md` line, and so do the classes that script finds or toggles, while the library's stylesheet goes: `references/maps/bootstrap.md`) and only its look changes; what cannot be styled is one line in `GAPS.md`.

## Step 1: the page loads AtomicAUI
Before you ask anything, read `specs/` and look in `../` for the page's source. **A one-shot task** (the prompt gives the whole job and no one is there to answer): write each unknown as a line in `GAPS.md` and go on; do not stop to ask which page or what to change.
Copy the stylesheet and set the page up: `node ../atomicaui/scripts/standard-copy.mjs <your static files folder>`, then the four attributes and the links of `../atomicaui/references/standard/start.md`. Inside a page you do not own: `aui-px.css` and the attributes on your own element only. A page in scope inside a layout you keep (a shared `_Layout.cshtml`): the layout stays as it is, so the page's own markup carries the stylesheet and script links (a `<link>` and a `<script>` in the page body are valid) and one element with the four attributes around its page frame and its dialogs, and the frame is marked `data-aui-panes="page in-layout"`: `check-standard` then measures that element only, its panes (PN-1) from the frame, and the kept bar, container and footer are not measured and not restyled. Without a server of your own, `node ../atomicaui/scripts/serve-folder.mjs <folder>` shows plain files.

## Step 2: list what the page holds. Do this before you change anything.
Start the page, then run `node ../atomicaui/scripts/restyle-inventory.mjs --url <address of the page> --views views.json`. A state that needs a click (an open dialog) is a view with `click`, as in `evidence.views.json`. **Content that appears only after something is done is part of the page.** A result table that a search draws, an opened item, a filter box that shows after a click, a dialog: each is a view whose `click` steps do it (type a word in a box, press Search, open the row), written in `views.json` before you run the inventory; the format is in `../atomicaui/references/token-check.md` (`{ "fill": "Product", "with": "pump" }`, an `<input type="button">` by its value, an element with an `onclick` by its text). **Every page is listed once as it opens, as a view without steps, and each state reached by typing or clicking is one more view of that page, with steps**: `[{ "name": "documents", "url": "/Documents" }, { "name": "documents-results", "url": "/Documents", "click": [{ "fill": "Product", "with": "pump" }, "Search"] }]`. A view with steps is read only after them, so a page that has only such views is never inventoried, compared or checked as it opens. A view that is not listed is not inventoried, compared or checked, and `restyle-done` cannot see it: a whole app lists every page as it opens and every state its pages reach, with the words that make them appear. A step that finds nothing fails the run. What a step sets going is waited for before the page is read: a page the step loads again, and an answer it asks for in the background (a search that fetches its result), up to 5 seconds (`../atomicaui/references/token-check.md`); open the pictures and see that each result is on its view. **A control a step cannot press yet** is one that is no button, link, tab, tree item or cell and has no `aria-label` and no `onclick` attribute, because a script binds its handler (`addEventListener`, jQuery `.on('click')` on a `<li>`, `<div>` or `<span>`), or an image named only by its `alt`. The old page is not edited to make it pressable (the inventory comes before any change), and the page is never dropped from the record: keep its view as it opens, leave out only the view of that state, restyle what the state shows all the same, and write the state as one line in `GAPS.md` and in your final message as not inventoried, compared or checked. Run it once, before any change, for the whole scope: each page in scope is a view whose `url` is the page's path (`loans.html`, `/Loans`), because a second run overwrites `restyle/`. A page you must read again later comes from a copy of the old folder kept in `restyle/old/` (or git): neither `restyle-done` nor `check-standard` reads `restyle/` as the app, also when you give the whole app as `.`. Then add a "Not done" list at the end of `restyle-map.md`: every page or element outside the scope.
It writes, into `restyle/`: `restyle-map.md` (every kind of element, how many, one place to find it, a suggested level), `restyle-before.json` (every text and every control, role and name) and pictures. Open the pictures. A row marked `ask` is yours to settle.
It reads one stack's pages in any language: it opens the running page.

## Step 3: the map
Fill the last two columns of `restyle-map.md`: the level you used, and what stays (handlers, names, values, validation). Every row says a level (a row of a page or element the task leaves out says "not done"): `restyle-done` fails a row whose "Level used" is empty (step 6). Take the mapping page of your source: `references/maps/html.md`, `bootstrap.md` or `dotnet-default.md`. Say it before you edit. The column "Recipe file" names the file whose recipe you copy for that kind, and its class list is copied whole, never a stylesheet of your own. The "Not done" list of step 2 names each page left out by its file (`item.html`): given page files instead of a folder, `restyle-done` fails any other `.html` page in the folders of those files that still loads an app stylesheet and is not on that list (step 6; a page the kit ships is never read). A kind with no recipe is level 3 (`SKILL.md`), never a CSS rule. A checkbox, a switch or a radio keeps its visible label as its accessible name (`aria-labelledby` the recipe says), or `restyle-compare` fails a control that lost its name.

## Step 4: in this order
1. The frame: page setup and layout (`../atomicaui/references/standard/recipes/layout.md`), then the top bar: it keeps its element (`<nav>`, `<header>`) and takes the class list of `view-toolbar` (`../atomicaui/references/standard/recipes/view.md`), as the map says. Each link in it takes the whole link class list from `top-bar-links` (`../atomicaui/references/standard/recipes/top-bar.md`), keeping its address, role and `aria-current`. A bar that runs from edge to edge of the window has no corners, on the bar only (`aui-shape-none`, as the recipe has it): its buttons stay soft. A bar with space around it stays soft (`aui-shape-soft`). The top-bar blocks are for a new page: their bar class list is a `<div>`'s. One shared layout or partial, once, and only when every page that uses it is in scope (above).
2. Shared partials and components next: a select, a dialog, a button. A Razor partial or Blazor component holds a recipe whole and takes only texts, ids and state; the class lists of a state are chosen whole, never built from pieces. The dialog recipe names a dialog "<title> Close"; record that difference.
3. Then screens, one at a time. Commit after each.
4. Delete the old styling last, from every page of the scope, the same day: the old stylesheet itself (the file, and its `<link>` on every page, the form and the dialog page too; one that a page outside the scope still uses stays: above), `style` attributes, old class names (a class a kept widget script needs stays (`references/maps/bootstrap.md`)). A widget you aligned keeps its own stylesheet.
An old app with many findings: while you work, record them first, `node ../atomicaui/scripts/check-standard.mjs <the pages, scripts and CSS in scope, and the aui/ folder> --url <page> --baseline check-standard.baseline.json --record`. Later runs without `--record` fail only on a new finding, and the file can only go down. A run that looks at fewer pages or folders compares only those; `--record` keeps the findings of the others. The baseline is for work in progress only: done is zero without it (step 6), and the file is deleted then.

Work through one kind of element or one page at a time. A first `restyle-done` pass that says NOT DONE with many problems is normal: fix one kind, run it again, and continue until zero. Never restore the old pages or stylesheet; if a bulk edit fails, narrow the next edit to one kind or one page. Use `node scripts/aui-class.mjs` to get a class list for a re-classed element, not a list typed from memory.

## Step 5: prove it
Run, with the page running, each on every page and state:
| Command | It says |
|---|---|
| `node ../atomicaui/scripts/check-standard.mjs <the pages, scripts and CSS in scope, and the aui/ folder> --url <address> [--views views.json]` | class lists are recipes, no raw look, no look written by a script, spacing rules; with `--views`, each view of the file after its steps |
| `node ../atomicaui/scripts/check-conformance.mjs --url <address> [--views file]` | every colour, font, size and corner is a theme value, in light and dark (`../atomicaui/references/token-check.md`) |
| `node ../atomicaui/scripts/check-behaviour.mjs --url <address>` | select, dialog and tabs behave as the React parts |
| `node ../atomicaui/scripts/restyle-compare.mjs --url <address>` | every text and control of the old page is still there, with its role and name |
Give it the folders or the files (it takes both) of the pages, scripts and CSS in scope (in an MVC app the `Views/` and `Content/` folders and the scripts: the `Scripts/` folder, or, when it also holds unminified libraries the app did not write (`jquery.validate.js`, `jquery-ui-1.12.1.js`), each script file of your own by name; a script that is not given is not read by `check-standard` (`restyle-done`, step 6, adds the scripts of your own that your pages load), and a finding in a library is never fixed in the library or allowed there), and always the copied `aui/` folder (each of its files is compared with what the kit shipped) and `aui-align.css` when a widget is aligned: never a shared layout, partial or stylesheet that the scope leaves as it is, and not the folders of other people's code (`lib/` and `vendor/` are skipped). A check that says SKIPPED or NOT CHECKED measured nothing: say so. Then open `restyle/after/` beside `restyle/before/`, light and dark, wide (1440) and narrow (390). At narrow width the page never scrolls sideways and every table is readable: a table whose columns do not fit 390 px is the `table-scroll` recipe (`../atomicaui/references/standard/recipes/table-wide.md`) with `aui/aui-behaviour.js` loaded, so it scrolls inside its own frame. Never a wrapper box, an overflow class or a pinned column the source did not have. `check-standard` fails a table that is wider than its frame and cannot scroll. Panes stack in one column by themselves (`aui/aui-behaviour.js`): add no class for it. A new control `restyle-compare` lists (a dialog's close button) is standard behaviour of a part: record it. A fold arrow the old page wrote as a character (`▾` or `▸` before a tree row) is not asked for, as a text made only of it or in a tree item's name: the tree recipe draws its own arrow, so the old character is never put back, and `restyle-compare` lists it as a note. A text with a word beside the arrow (`▲ 12%`, `Name ▲`) and the name of any other control are compared as they are.

## Step 6: done is one command, and it must say ok
Before the word "done", "restyled" or "follows the design system", in your final message or anywhere, with the page running:
```
node ../atomicaui/scripts/restyle-done.mjs <every page, script and stylesheet in scope, and the aui/ folder> --url <address of the restyled page>
```
It exits 0 only when all four hold, and it says each one that fails: (1) no page of the scope links a stylesheet of the app's own, no such file is left in the scope (`--keep <file name>`, once, for the one that must stay, with its line in `GAPS.md`: pages outside the scope still use it as it is, ``- Kept for pages outside the scope `<name>`: which pages`` (`check-standard` skips it then, it is never re-tokened, and a page of the scope that still links it fails); or it holds only the show and hide rules of a kept widget script, ``- Kept stylesheet `<name>`: which widget script`` (`check-standard` reads it like your own CSS); the own stylesheet of a widget you align stays when it is in `lib/`, `vendor/` or `node_modules/`, or has the line ``- Aligned widget stylesheet `<file name>` of `<widget>`: which pages`` beside the widget's own ``Aligned widget `<widget>` `` line and its `data-aui-aligned` mark on a page of the scope, and `check-standard` skips it then too; an `@import` in a `<style>` block counts as a link, and a link to another host (a CDN, an intranet theme, a web font) counts like a local one: the typeface comes from `aui/`; given page files instead of a folder, every other `.html` page in the folders of those files (read down; never one the kit ships, nor `restyle/`) that still loads an app stylesheet is under "Not done" in `restyle-map.md`), every `.html` page of the scope (a file with an `<html>` element: a fragment a script loads is measured in the page that loads it) is a view of `restyle/restyle-before.json` (one address opens one page; a page a server draws, such as `.cshtml` or `.razor`, is not matched to an address: put each one in your views file yourself), and the copied `aui/` folder is among the paths; (2) `check-standard` reports zero problems on every view of the record (typed views after their steps), desktop and narrow, light and dark, with no baseline (a missing browser is a failure, not a pass), on the paths you gave and on every script file of the app's own that a page or layout of the scope loads with `<script src>` and that is not among them: it is found beside the page, or under the folders you gave and the folder you run in, and the line "restyle-done: also read ..." names each one added, so a script you forgot is read all the same (never a script of another host, a library by its name, a minified file, or one in `lib/` or `vendor/`; a script it finds no file for is named as not read, and that is NOT DONE, never a pass: run the command in the app's root folder, or give the script's file or folder); (3) `restyle-compare` finds every text and control of the old page, with role and name, in every view; (4) `check-behaviour` finds no problem in a select, a dialog or a tabs part of any page of the record, each as it opens: a part that differs from the React part is NOT DONE (a select whose values are not its option texts passes with each value in `data-value` on its option, `references/maps/html.md`), and so is a dialog that does not open, a console error while a part is used, and steps that never came to rest. Three things it prints do not stop "done", and each is yours to say in your final message: a dialog that differs only in where its focus starts or the order of its buttons (the old page or the spec decides those, AUI-08: focus on another place inside the dialog (a button, the dialog itself, its title or description), a button there on both sides with another name or class list; another role, tab stop or attribute of a button, focus that leaves the dialog, a button gone or added, or a change of the layer or the page behind is NOT DONE), a part it leaves NOT CHECKED, and a page with none of the three parts. It also fails while a row of `restyle-map.md` has an empty "Level used" cell (step 3). A check-standard that reports problems is not a finish: fix them and run it again until zero. Fix the page, never the check. Paste its `restyle-done:` result line: `restyle-done: ok`, or `restyle-done: NOT DONE` with what failed. Any other result: say "not done" and which step failed.

After NOT DONE, read the grouped remaining problems and its `Next:` command. Fix one kind or one page and run the command again. The problem count is the total on the `Remaining in all:` line: every file added up, a finding on several pages once for each, so one page fixed in a run lowers it. If the same problem count appears three runs in a row, stop, paste the problem list, and say what is left.

## End with
- Per kind of element: the level used. Where a recipe, a styled piece or an aligned widget stands in: its line in `GAPS.md`.
- Each command and its result line, pasted (for `restyle-done`, the `restyle-done:` line). What was not run. Pictures you opened.
- **Checks before claims.** Paste the result lines of the checks of step 5 and the `restyle-done:` result line of step 6 (`restyle-done: ok`, or `restyle-done: NOT DONE` with what failed) before you claim anything; a check you did not run is "not run", never "passed". Write your final message and the checklist before the last full run (`npm run verify` where the app has it), its line saying "verify not finished", then put its last line in both when it ends. Wait for that last line: never end a turn, and send no message, while a command you started still runs.
- Practice first: `../atomicaui/references/samples/legacy/html/` and `../atomicaui/references/samples/legacy/razor/`, with their answers.
